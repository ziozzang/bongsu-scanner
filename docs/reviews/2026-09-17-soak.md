검증 대상에서 **Docker export 취소 시 대용량 임시 파일 누수(P1)**, **가상 메모리 1 GiB 제한 시 런타임 abort 및 종료 코드 오분류(P2)**를 재현했다. scan 200회와 유효한 카탈로그의 match 50회는 모두 성공했고, RSS·FD의 지속 증가나 카탈로그 손상은 관찰하지 못했다. 컨테이너 전체 완주는 시간 제한으로 미검증이다.

- 갱신과 겹친 초기 match 50회는 모두 lock 오류로 종료 1이었다. 이후 **별도로 50회 전부 성공한 유효 soak**를 완료했다. 초기 오류와 재시험을 부록에서 구분한다.
- wall은 `time.monotonic()` 기반 시작~reap 시간, RSS는 `os.wait4(pid, ...)`의 `ru_maxrss`(KiB). `/proc/<pid>/status`, `/proc/<pid>/fd`를 시작 2초 동안 50ms, 이후 200ms 간격으로 관측했고, 각 실행에서 가능한 경우 `ls -l /proc/<pid>/fd`도 저장했다. FD 최대치는 샘플 최대이므로 순간 peak를 놓칠 수 있다. wall에는 최대 약 200ms polling 지연이 포함된다.
- scan/match 각 반복군은 순차 실행했다. 일부 자원·컨테이너·보조 시험은 겹쳐 실행했고 공유 머신의 다른 부하도 있어 시간 차이를 회귀 성능 결함으로 단정하지 않는다. CLI 측정 대상에 별도 watchdog을 두었으며 강제 watchdog kill은 **0회**였다.

## 우선순위별 결함과 정확한 재현

### 1. P1 — Docker export 취소가 GiB 단위 숨김 임시 파일을 남김

영향: 정상 운영의 Ctrl-C 또는 timeout 반복만으로 디스크를 채울 수 있다. 병렬 host 검사에서 합계 약 8.18 GiB 잔류. 단일 컨테이너에서 2초 timeout은 2,505,415,680 bytes, 1초 후 SIGINT는 1,227,223,040 bytes 잔류를 재현했다. 종료 자체는 각각 1/130으로 정상 매핑됐고 hang은 없었다.

```bash
W=/home/ziozzang/.cache/bongsu-work/w1
export BONGSU_HOME="$W/home"
mkdir -p "$W/container-timeout-tmp"
TMPDIR="$W/container-timeout-tmp" "$W/bscan" scan --no-sign \
  --format cyclonedx --output "$W/container-timeout" --timeout 2s \
  container://auto-ontology-api-1
# exit 1: bscan: context deadline exceeded
ls -la "$W/container-timeout-tmp"
# .tmp-bongsu-container-1544059140.tar1004082338  2505415680 bytes

mkdir -p "$W/container-sigint-tmp"
TMPDIR="$W/container-sigint-tmp" "$W/bscan" scan --no-sign \
  --format cyclonedx --output "$W/container-sigint" \
  container://auto-ontology-api-1 &
pid=$!
sleep 1
kill -INT "$pid"
wait "$pid"
# exit 130: bscan: interrupted
ls -la "$W/container-sigint-tmp"
# .tmp-bongsu-container-1965456807.tar4260808239  1227223040 bytes
```

위 컨테이너는 시험 시 이미 실행 중이던 `auto-ontology-api-1`(ID `a5bc08bf76c5`)이다. 다른 환경에서는 export가 timeout보다 오래 걸리는 실행 컨테이너로 대체한다. 임시 파일의 랜덤 이름·크기는 달라진다.

파일/함수 힌트(빌드 커밋 기준): `internal/scan/image.go:153 runDocker`, `:174 tempArchive`, `:289 dockerContainer`. `dockerContainer`는 `bongsu-container-*.tar` 하나만 defer-remove한다. `docker export -o <path>`가 옆에 만든 `.tmp-<basename><random>`을 `exec.CommandContext`의 child kill 뒤 제거하지 않는다. 검토 방향: 전용 임시 디렉터리를 만들고 전체 정리하거나, bscan이 연 파일에 Docker stdout을 직접 연결해 파일 수명 관리를 소유한다. Docker image save 경로도 동일 패턴이지만 이번에는 별도 재현하지 않았다.

### 2. P2 — 1 GiB RLIMIT_AS에서 runtime abort, 문서상 findings 코드 2로 종료

`ulimit -v`는 RSS 제한이 아니라 가상 주소 공간 제한이다. 낮은 RSS에서 실패한 것은 그 자체로 메모리 누수 증거가 아니다. 다만 사용자가 요청한 “명확한 CLI 실패 또는 graceful degradation” 대신 런타임 스택 덤프가 발생하고, `--fail-on`을 쓰지 않았는데 exit 2를 반환한다. 단독 제한 3/3 및 FD 제한 병행 1/1에서 종료 2와 런타임 덤프를 재현했다. 단독 시험의 마지막 재현은 `fatal error: out of memory`였고 나머지 세 실행은 `pthread_create failed`/SIGABRT였다.

```bash
W=/home/ziozzang/.cache/bongsu-work/w1
export BONGSU_HOME="$W/home" TMPDIR="$W/tmp"
(ulimit -v 1048576
 "$W/bscan" scan --no-sign --format cyclonedx \
   --output "$W/limit-vmem" --timeout 120s host)
# exit 2, 약 0.255초
# runtime/cgo: pthread_create failed: Resource temporarily unavailable
# SIGABRT: abort

(ulimit -v 1048576; ulimit -n 256
 "$W/bscan" scan --no-sign --format cyclonedx \
   --output "$W/limit-both" --timeout 120s host)
# exit 2, 동일 runtime abort
```

파일/함수 힌트: `cmd/bscan/main.go:46 main`, `cmd/bscan/match.go:50 exitCode`, `internal/scan/walk.go:1189 walkParallel`(기본 worker=min(8,CPU)), `internal/scan/catalog.go scanDpkgStatus/paragraphs`. 첫 덤프의 활성 작업은 dpkg status 파싱과 GC였다. 첫 실패 지점은 Go/cgo thread 생성이고 다른 실행에서는 Go runtime OOM이었으며 **특정 scanner 함수의 누수로 입증된 것은 아니다**. 런타임 fatal은 일반 error 반환 경로를 거치지 않으므로 exitCode만 수정해서 해결되지 않는다. 검토 방향은 실행 초기 RLIMIT_AS 점검·지원 가능한 제한의 문서화·worker/런타임 설정 검증이다.
